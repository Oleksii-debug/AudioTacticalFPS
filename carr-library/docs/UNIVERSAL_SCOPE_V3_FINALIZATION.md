# Resonance — current technical specification and finalization

## Current engineering decisions — Resonance, 2026-11-27

**Product:** «Резонанс» / Resonance, a platform by Sceneria Innovative Technologies for voice cloning and speech, accessible reading, audiobooks, transcription, translation, music/audio production, libraries and scientific research. Public feature descriptions describe the intended platform; they do not certify the current build.

This existing finalization document is the entry point for the current product scope and architecture. Read it with the detailed V3 audio/agent specification and the V2 library contracts. Where older wording conflicts, these current decisions and later explicit owner instructions prevail. Root [AGENTS.md](../../AGENTS.md) governs worker coordination; roles and claims are advisory, not exclusive locks. Historical PR numbers, test counts and baseline SHAs are evidence snapshots, not permanent implementation authorities. Read the live integration record in [issue 1](https://github.com/Oleksii-debug/AudioTacticalFPS/issues/1).

### 1. Scope, traceability and honest status

Retain all requested library, research, reader, voice, studio, transcription, music, translation, recovery, accessibility and secure-delivery workflows. The platform is no longer limited to the owner's private use; owner-private installation is one supported profile. Keep confidential deployment, account and commercial policies separate from public technical contracts. This review does not publish software, select prices or activate a paid service.

For every requirement record: requirement ID, supported scenario and limitation, existing module/adapter, exact source and pack identity, integration status, runtime test, Windows/NVDA evidence, rights decision and remaining dependency. Use separate states: REQUIREMENT, SOURCE_REVIEWED, ADAPTER_PRESENT, INTEGRATED, EXECUTED, QUALIFIED, DISTRIBUTION_CLEARED, with FAIL/NOT_RUN/WAITING_INPUT where appropriate. These are independent dimensions: an adapter can exist while its model has never run; a passing runtime can lack redistribution clearance.

“Like Balabolka” means familiar accessible reading/synthesis workflows, independently implemented. Maintain a finite checklist of the requested functions from official documentation; do not introduce a moving, unlimited promise of identical behavior or all features of any third-party application. Preserve requested formats and workflows in the checklist; mark each supported, limited, pending or unsupported with evidence. Reuse existing code, never copy that application's proprietary code/assets or imply affiliation.

A guided command parser is not proof of a local language-model agent. A registered voice is not proof of voice cloning. A MIDI/looped or synthetic long-file test is not proof of hours of original neural music. A 135-entry catalog is not proof of every feature in 135 languages. Translation, ASR, OCR, UI localization and each voice/model pair have distinct coverage.

### 2. Reuse and integration order

1. Reuse the current canonical module and its contracts.
2. Inspect existing PRs and select already implemented, reviewed changes, reconciling overlaps by exact file/commit identity.
3. Adopt a mature upstream library or engine at a reviewed revision through the same adapter boundary.
4. Write only the missing glue, accessible workflow or verified behavior gap. Do not build another OCR/search/DSP/ASR/model-training framework.

For each adoption retain source URL, commit/release, artifact hashes, licenses/notices, transitive/native/model dependencies, supported Windows/hardware profile, actual API/offline tests and the reason it replaces or extends existing work. The [reuse ledger](REUSE_DECISIONS_V2.md) records selections and candidates; it is not a second specification. Whole applications can be interoperability targets when direct embedding would duplicate the UI, database or licensing burden.

Existing integrated candidates already contain narration, engines, production, provider credentials/budgets, assistant plans, command registry, backup sidecars and CSL processing. Discover their latest accepted versions before creating anything. Do not restart these modules because an old task calls them missing.

### 3. Architecture: one desktop platform with isolated engines

Retain Python/wxPython, SQLite/FTS5 and the current application service boundary. UI, CLI, scheduled operations and the assistant call the same domain services. Keep native accessible controls and the existing command registry. Long OCR/inference/rendering never runs on the UI thread or inside a long database write transaction.

| Layer | Reuse / responsibility | Boundary |
|---|---|---|
| Desktop | Existing wx controls, command registry, settings, reader and studio | Accessible commands, focus, progress; no duplicate business logic |
| Domain | Current catalog, source/citation, research, reader, production services | Workspace authorization, immutable originals, versioned derived work |
| Operation facade | Existing ingest journals, audio jobs, assistant state and backup producers | Shared job identity, progress, cancellation, resource admission and recovery view |
| Engine adapters | Existing extraction, voice/model, FFmpeg, semantic and provider interfaces | Versioned capabilities and bounded inputs/outputs |
| Heavy runtimes | Reviewed OCR/voice/ASR/music/LLM processes or isolated local services | Separate dependency environments and CPU/GPU/disk/device budgets |
| Persistence | Existing SQLite schemas, immutable assets and typed state files | Transactional publication, migrations, reproducible provenance |
| Delivery/services | Existing packaging plus reviewed update/entitlement adapters | Signed artifacts, offline verification, optional authorized networking |

Do not introduce microservices, a web replacement UI, a second catalog, a new universal database or an all-at-once queue rewrite. Build a common facade incrementally around existing stores. Isolation is a dependency/crash/security boundary; it does not automatically resolve a third-party license obligation.

### 4. Shared contracts to complete

**Capability record:** stable adapter/engine ID, protocol/schema version, source revision, model/voice/pack hash, supported languages and pairs, formats, controls, device/precision needs, offline/network behavior, rights profile, maximum request/context size and qualification evidence. Missing capability is visible and must not silently switch language/provider. Reuse current model manifests and voice registry.

**Operation record:** job/parent ID, workspace/project, input source revision and hashes, selected adapter/model and settings digest, budget, state, completed artifact identities, checkpoint, timestamps and categorized error. Preserve queued/running/paused/cancelled/failed/completed/waiting-input distinctions. “Completed” requires durable validated outputs. Re-running after a crash must not duplicate a committed import, paid request or rendered segment.

**Resource broker:** admit heavy CPU/GPU/disk work and exclusive microphone/device use through one cooperating policy. Release reservations after crashes/cancellation; keep the UI and basic reading responsive. These runtime resource limits do not impose worker/PR orchestration caps.

**Engine session:** prefer a reviewed persistent local worker for many segments where supported. Verify runtime/model identity at admission and invalidate it on changes; do not weaken content or cache integrity. Benchmark load cost, sustained throughput, memory/VRAM and recovery before claiming large-book performance. Repeated full model loading/verification per short chunk is a measured optimization candidate, not a reason to rewrite the engine.

**Planning:** retain the deterministic parser and typed allowlisted executor. A local LLM adapter can produce the same versioned plan; validate capability, arguments, paths, budgets and approvals before execution. No direct shell/filesystem/network authority for model output. Prompt text and imported documents are data, never application policy.

### 5. Audio, cloning and transcription integration

Use existing voice/engine, narration, scene/timeline, FFmpeg, render-job and model-manifest modules. Source text, editable narration, pronunciation rules, voice identities and output artifacts remain distinct. Professional studio acceptance separately covers microphone capture, track/clip editing, real-time monitoring/playback, offline rendering, each requested effect, LUFS/peaks, stems and keyboard/NVDA operation. A filter list or render script alone does not satisfy the whole studio.

The owner's existing local voice-cloning engines and dordiai-voices remain the primary integration path. Review the supplied runtime/API when available; do not train or substitute a competing engine. Confirm reference rights, multilingual intelligibility/similarity, actual controls, long-form consistency and supported hardware using real authorized samples. SAPI4 is legacy compatibility only on explicitly verified combinations, not a promise that every old driver works on Windows11 x64.

**Transcription input has now been supplied for review.** The owner-provided Whisper Transcribe implementation is the starting point; reuse its actual worker and protocol after provenance, dependency, privacy, correctness and Windows checks. Retain offline transcription, timestamps, TXT/SRT/VTT/JSON, batch/cancel/resume and editing. Speaker diarization and additional models remain separate capabilities requiring real evidence. Do not replace the supplied application with another fresh Whisper stack or publish its jobs, recordings, transcripts, virtual environment, caches or private paths. Source availability advances review, not integration/quality acceptance. A library/audio preview may ship with this module explicitly pending; it must not be described as the complete promised platform.

### 6. Translation and optional networking

Add official Google Cloud Translation through the existing provider gateway, credential vault, budgets, derivative-text storage and job lifecycle. Basic v2 and Advanced v3 have different authentication/features; select explicitly. Never scrape consumer endpoints or embed a shared key. Discover the selected provider/model's actual source/target coverage, preserve originals, preview external transfer and cost, and record translation provenance. An offline translator is a separate reviewed engine; do not promise Google-equivalent features or arbitrary languages offline.

Core installed local operations require no cloud inference. Initial model installation, user-approved external translation/research services, update checks and entitlement refresh are separate network purposes with separate consent/policy and failure handling. “Offline” must be verified for the actual runtime, including native processes; Python flags/audit hooks alone are not a native-code sandbox.

### 7. Persistence, backups and capacity

Preserve immutable original bytes, edition/source identity and verified quotation offsets. Corrections, translations, transcripts, narration, generated audio and research notes are versioned derived assets with provenance; they never silently become original evidence.

Extend existing typed backup producers to cover pending import/render/ASR jobs, required inputs, project settings, reading state and recovery drafts. A backup manifest must say exactly what is included, excluded, external or re-downloadable. Credentials stay separate with explicit recovery; licensed packs are copied only if permitted. Restore into a new destination, validate hashes/schema/references and require review before resuming external operations. Do not call a completed-library snapshot a complete machine/project migration while queues or required inputs are omitted.

Existing file-count, byte and hard-link/filesystem limits are safety bounds, not scale benchmarks. Raise them only with measured fixtures, streaming design and regression evidence; do not delete guards to claim “tens of thousands of books.” Record p50/p95 import/search/open latency, peak RAM/VRAM/disk, cancellation latency and recovery results on a declared hardware/corpus profile. Numerical targets must be set from the intended support profile and actual baseline, not invented in promotional copy.

### 8. Rights, entitlements and updates

The brand and original application/integration work are distinct from upstream copyright. The installer and accessible About/Licenses page must preserve each component's actual terms and notices. Approve exact code, native binaries, weights, voices, samples, fonts, SoundFonts, styles and assets separately. GPL/AGPL permit commercial activity but impose obligations; an IPC boundary or “private” ZIP does not automatically waive them. NC model weights are not included in an unrestricted commercial-use pack without additional rights. Audit the actual shipping dependency tree.

Maintain separate per-profile distribution manifests. Existing personal-use experiments remain available within applicable terms; they do not establish general distribution clearance. Code signing proves publisher/integrity, not safety, ownership of dependencies or quality. Secure release, update and license verification use reviewed implementations; no custom cryptography.

Keep unattended signed entitlement refresh independent from offline validity/grace, updater activation and billing. Test cadence and outage recovery with synthetic policies; keep actual service endpoints, intervals and business settings private. Outages must not interrupt saving/render completion or remove access to user-owned work and exports. Signed offline renewal/recovery remains possible.

### 9. Delivery sequence and acceptance

First reconcile current runnable candidates, fix observed installed-Windows failures and verify original-data/recovery/accessibility regressions. Then integrate qualified owner engines, Google/local translation, transcription and the missing professional-studio/agent capabilities through the shared boundaries. Engine exploration and other independent work can continue in parallel. Complete per-language quality qualification against the canonical 135-entry target after the core is stable.

A preview, a qualified module, an owner test build and a distributable platform are distinct deliverables. [Acceptance](acceptance.md) defines the gates; do not shrink the promised product to make a release green. Do not make missing Carr books block unrelated platform acceptance. Keep actual corpus acceptance separate. Never transfer test counts or PASS from a different SHA, dependency pack or installed artifact.

### 10. Worker responsibilities

[COMMON.md](../automation/COMMON.md) and [ROLES.json](../automation/ROLES.json) carry the current fifteen advisory lanes. Keep existing automation IDs, cadence and enabled state. Each run reads current source and existing changes, completes a useful integration/review step, saves evidence and continues other safe work when one dependency is unavailable. No exclusive coordinator, claim lease or CI queue may stop independent useful work; all correctness, rights, privacy and release evidence requirements remain.

## V3-16 — Defense-in-depth, private code and data protection
- Threat model: unauthorized copying/distribution, tampered installer/model/update, malicious document/archive/codec/plugin, prompt injection, credentials/PII exposure, privilege escalation, data loss and dependency compromise. An inventory and selected source/API review identified suitable existing modules; actual integration, license/ownership authorization and compatibility tests remain required. No private code copied into public Git. The public integration contract stays product-neutral; sensitive mapping and private package adapter are kept separately.
- User-facing installed experience: one signed user-facing Resonance launch entry (retain existing internal filenames and compatibility launchers until a tested migration), Start-menu shortcut, normal uninstall and repair; no requirement to navigate Python files, scripts, model folders or DLLs. Evaluate native compilation/packaging (e.g. reviewed Nuitka build or compiled critical components), standard Windows installation layout, ACLs/least privilege, internal resources in package or ordinary protected application directories, exclude development source/test fixtures/debug symbols/unneeded tools from private release.
