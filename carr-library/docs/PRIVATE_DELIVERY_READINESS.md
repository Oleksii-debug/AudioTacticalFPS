# Private delivery integration readiness

## Implemented host lifecycle

The existing versioned delivery boundary now has an optional host service and
native Help > License and updates / Check for updates commands. The same service
is available through the explicit delivery CLI. Private assembly injects the
provider and build context; user settings never name or load executable modules.

The host supports local status, signed-file import/export, separately approved
renewal, update checks and downloads, offline update import, recovery inspection,
and explicit installation. Offers are display data. A current verified
preparation and a fresh one-use approval are required for installation. The
existing complete library backup producer runs first, including retained
generated assets; backup failure, cancellation, changed staging or active work
prevents activation. Providers must reverify trusted metadata and staged bytes.

Unattended renewal uses the existing desktop executor. Initial status/signature
reads occur on that worker. Private policy supplies the authorized cadence,
retry bounds and jitter; no production interval is selected by public code.
Synthetic tests distinguish 7-day and 14-day schedules from offline validity.
Absent, review-required and perpetual profiles do not enroll or refresh
implicitly. Outages retain the provider's last verified state; background work
does not take focus or emit progress audio. Closing cancels pending work.

## Evidence and separation

Independent review corrected an initial status read on the UI thread and
stale update approval after backup. The final composed Python 3.12/Linux host,
CLI, desktop, saved-draft and JSON-reader gate completed 158 passed with zero
skips, including those negative controls and the real backup path. Later
library/audio lifecycle checks completed separately. Actual installed native
Windows execution is still required on the final integrated commit; the
portable gate does not qualify a Windows installer or a production authority.

The public tests use synthetic providers and real host/SQLite/backup state.
They do not prove signatures, publisher identity, production trust or an
operating system installer. Actual owner-runtime adapter qualification remains
a separate private evidence set. No private implementation, issuer keys,
deployment endpoints, account records or business policies are included here.

## Preserved access and remaining authority

Provider declarations remain declared_unqualified. Typed responses must match
the exact context; malformed, incompatible or unavailable replies are redacted.
Reserved reading, saving, export, backup, restore, recovery, settings and
active-job completion actions remain independent of entitlement. Default
assembly has no private provider and introduces no licensing restriction,
account, payment, automatic networking or changed delivered rights.

A usable private provider requires reviewed trust roots, product/device and
policy binding, signed expiry and freshness, protected durable state, key
rotation and crash recovery. An update additionally requires signed
product-bound freshness, rollback protection, package provenance, verified
staging, a supported installer and actual version A-to-B/data-recovery tests.
Metadata hashes alone do not authorize activation. An owner endpoint and signing
facility must be configured privately before website delivery. No generic
adapter declaration or synthetic native control test closes those requirements.
